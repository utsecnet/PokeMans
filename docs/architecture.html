00The whole system

Everything in one frame: where code is written, how it reaches production, and what talks to what once it is there.

How a change reaches production

  1. Claude edits the repo on your laptop, then builds, lints and runs the 298 tests locally.
  2. A commit lands on a feature/* branch — on request, never unprompted.
  3. You push. ci.yml runs, and Cloudflare Pages posts a preview URL for that branch.
  4. You review the preview. Merging to main runs migrate.yml, then deploy-api.yml, and Cloudflare rebuilds the frontend.
WorkflowTriggerDoes
ci.ymlevery push and PRTypecheck, oxlint, build, 281 + 17 tests. Everything else gates on this.
migrate.ymlmerge to mainApplies Supabase migrations — always before the API that depends on them.
deploy-api.ymlafter migrateflyctl deploy of the Express container.
sync-prices.ymlschedule, 06:00 UTCCalls /internal/sync. Not part of the deploy chain.

The frontend gets no workflow at all. Cloudflare Pages' native GitHub integration builds and deploys on push with no YAML and no secrets, and gives a free preview URL per branch — writing an Action to do the same job would only be worse.

Two consequences of the repository being private are worth recording. Scheduled workflows are disabled after 60 days of inactivity in public repositories only, so the daily sync — which is also what keeps the Supabase project from pausing — is not at risk from a quiet stretch. And the working tree is now a single git repository rather than an edit directory mirrored into a separate push repository: once a push triggers a deploy, two copies of the tree means the thing that ships may not be the thing that was reviewed.

01Hosting boundaries

Four parties run code or hold data. Only one of them runs code we wrote.

The shape below is chosen so that the expensive thing — a managed Postgres instance — comes from the vendor that gives it away at this size, while the cheap thing — a small always-on container — comes from the vendor that charges by the megabyte. Inverting that pairing is what produced the $38/month figure for the same workload.

Two details in Figure 1 carry more weight than their size suggests. Card art is fetched by the browser directly from images.pokemontcg.io and never passes through our infrastructure, which is why the egress line on every bill below is effectively zero. And the daily GitHub Actions run is not only the price sync — it doubles as the keep-alive that stops a free-tier Supabase project pausing after seven idle days, which pg_cron cannot do for itself because it stops when the project stops.

User count is not what ends the free tier. The catalogue is 11 MB against a 500 MB allowance, and a few thousand users sits far inside 50,000 monthly actives. The table that grows without bound is price history: capturing roughly 10,000 actively-tracked printings once a day accumulates about 3.6 million rows — 300–400 MB — per year. That is what eventually forces the $25/month Pro plan, most likely in year one or two, and Pro's 8 GB then covers about two decades.

Worth knowing before you design around it

Sign in with Apple requires the Apple Developer Program at $99/year — $8.25/month, more than double the entire hosting bill. Google and Facebook cost nothing. Launching without Apple is the difference between a $3.50 and an $11.75 monthly run rate.

Two of these move class in the migration. fx_rates and the shareable half of price_history currently sit in the local personal.sqlite — not because they belong to the user, but because local-first left nowhere else to put data that could not be re-fetched. Centrally, both become shared, and that is the single biggest change in the whole design: price capture cost stops scaling with users × their cards and starts scaling with distinct cards, which stops at the catalogue no matter how many people sign up.

04Data flow and trust boundaries

Three boundaries, each crossed by traffic that must be re-checked on the far side.

The API is not the only thing standing between one user and another user's collection. Row Level Security means the check lives in Postgres, so a bug in an Express route handler — a missing where user_id =, a query built from the wrong variable — returns nothing rather than returning someone else's binder. That property is worth more here than anywhere else in the stack, because the collection is the one piece of data in the system that cannot be rebuilt from an upstream source.

Process 5.0 is the exception, and deliberately so: the sync worker holds the service role and bypasses RLS, because writing the shared catalogue is exactly what no user is allowed to do. That key never leaves the Fly machine, which is the whole reason a separate API tier exists rather than the browser talking to Postgres directly.

05Licence routing for price data

The one flow where a correctness bug is also a terms-of-service breach.

Price rows arrive under two different agreements. Rows your own licence paid for may be served to everyone. Rows fetched with a user's personal API key belong to that user, and republishing them to other accounts breaches the agreement they signed, not one you did. Both land in the same table, so the classification has to be a column, checked on read.

The back door to watch

The leak usually does not arrive through an endpoint that returns the wrong rows. It arrives through a cache. A "market value" or "popular cards" rollup computed over whatever price rows are present will quietly fold one user's licensed data into a figure every other user reads. Aggregates must filter license_class = 'shareable' explicitly — never rely on table membership.

There is a legitimate way to own history outright: capture the current spot price daily under your own licence and let it accumulate. TCGdex exposes current prices and no history at all, which is exactly the shape that works — one call per card per day, and after a year you hold a year of series that no third-party licence restricts. It cannot be backfilled, so the cron is worth standing up well before the app is ready.

06Threat model

STRIDE, scoped to what actually changes when the app stops being single-user.

IDThreatSTRIDESeverityMitigation
T1 Supabase service_role key reaches the client bundle Elevation Critical Only the anon key ships to the browser. Service role lives in Fly secrets and is asserted absent from dist/ by a build-time check.
T2 Per-user licensed price rows surface in a shared aggregate or cache Disclosure High Every aggregate filters license_class. Enforced by a database view that excludes per-user rows, with rollups reading only the view.
T3 One user reads another's collection through a route missing its filter Disclosure High RLS policies on auth.uid() for every per-user table, so the check survives an application bug. Deny-by-default; no table ships without a policy.
T4 Encryption key stored beside the ciphertext it protects Disclosure High DEK held as a Fly secret, never in Postgres. A database dump alone yields no plaintext keys.
T5 An endpoint returns linked_accounts.secret Disclosure High Column excluded from every select list; API returns masked hints only. A column-level grant makes the mistake impossible rather than merely unlikely.
T6 Forged, expired or replayed JWT accepted by the API Spoofing High Signature verified against Supabase JWKS on every request; short expiry with refresh; clock skew bounded.
T7 A client writes to the shared catalogue or to another user's price rows Tampering Medium No write policy exists for shared tables, so writes fail at the database. Only the service role can write them.
T8 /internal/sync callable by anyone who finds it Tampering · DoS Medium Shared-secret header plus a single-flight lock, so a flood collapses to one run and cannot burn the day's API quota.
T9 Third-party quota exhausted or cost amplified by user-triggered fetches DoS Medium Price fetches happen only in the scheduled worker, never on a user request path. Central daily budget with backoff.
T10 OAuth token leaked via an unvalidated redirect target Spoofing Medium Redirect allow-list configured in Supabase; no user-supplied return URLs.
T11 Malicious or compromised npm dependency in the build Tampering Medium Lockfile committed, CI installs with npm ci, Dependabot on, and the sync worker's egress is limited to known hosts.
T12 Expensive search pattern degrades the API for everyone DoS Low Already mitigated — the glob matcher is linear-time two-pointer, not regex, with a perf test guarding against regression.

T1 through T5 are the ones that change character when the app opens to the public. In single-user local-first form, none of them have a victim: there is one user, one machine, and no adversary who benefits. Every one of them acquires a victim the moment a second account exists, which is why the boundary work in Figure 2 is not optional polish.

07Migration notes

What actually has to change in the codebase, in rough dependency order.

  • Split the schema by class, not by file. The current split is two SQLite files; the new one is catalog / market / app schemas with policies, in one database.
  • Add user_id and license_class to price_history. The table already carries service and source in its primary key, so classification is a routing rule on columns that exist rather than a restructure.
  • Move the provider registry's licence terms into data. The existing PROVIDERS array gains a licence class per entry, so adding a source stays a config change.
  • Relocate the DEK. It currently lives at %APPDATA%\PokeMans\secrets.key; in the cloud it becomes a Fly secret, and the encrypt/decrypt helpers read it from the environment.
  • Replace node:sqlite calls with a Postgres client. The query surface is small and already centralised behind helper functions.
  • Introduce sessions. Everything today assumes one implicit user; routes need auth.uid() threaded through, which is also what makes the RLS policies meaningful.

08Open questions

  • Does the price-history plan need a business licence now? Serving other users from your own key is what forces the upgrade. Accumulating your own history from shareable spot prices may not — it depends on each provider's caching and redistribution terms, which need reading per source, not assuming.
  • Is monetisation on the table? It changes the IP calculus around card art from tolerated fan project to commercial use, and it is the trigger for needing a licence rather than an exemption.
  • Do shared collections ever ship? A public binder link is user-authored but globally readable — a third ownership class that neither bucket in Figure 2 currently models.
  • Self-managed alternative. A single Hetzner CX22 at about €4.35/month runs all of this in one Docker Compose file and handles thousands of users at this workload. It trades roughly a dollar a month for owning backups, patching and TLS renewal.

09Hosted price layer

Supersedes the price half of sections 03 and 05. Those describe a multi-user service on Fly.io with per-user rows and license_class routing; that plan was dropped. What follows is the narrower thing actually being built — one user, local-first, with prices the only hosted data.

The partition is by volatility, not just by whether data is shared. Prices and card metadata are both shared across any future users, but prices change daily and the catalogue changes a handful of times a year, when a set drops. So prices are queried live and the catalogue is synced to the device and queried locally. A flat “shared means hosted” rule would put the card browser behind a network round trip on every keystroke and stop the app working offline.

Writes are delta-only: measured against the app’s own history, 87.3% of consecutive-day prices are exactly unchanged, median day-over-day move 0.00%. Storing every day for every card would be roughly eight times the rows for no extra information. Because the upstream republishes identical values rather than merely close ones, a plain equality check is enough — no tolerance threshold needed.

That is also what forces two tables. Delta-only makes the commonest read hard: “what does this card cost today” stops being WHERE captured_on = today and becomes the most recent row at or before today, which for a bulk common might be six weeks back. That is a latest-row-per-group scan over a table heading for millions of rows, run on every card grid. So price_current is rewritten in full on every run and answers it with a primary-key hit, while price_history stays append-only and is touched only when a chart opens.

Two consequences worth carrying forward. A delta-only series is a step function — each row holds until the next one — so anything drawing it as a plain line chart will invent smooth ramps across the gaps that never happened. And row level security is enabled with no read policy: adding one makes the tables readable by anyone holding the anon key, which ships inside any client bundle that uses it. That is the redistribution problem section 05 was written to avoid, arriving through a different door.

The fetch itself is unremarkable. TCGdex has no bulk pricing endpoint, so the job makes one request per card — 20,444 of them — which measured at 4.8 minutes and 43 MB at concurrency 8, with zero failures and no throttling. TCGdex is also the better source here despite the request count: pokemontcg.io returns prices in bulk, 250 cards per request, but its Cardmarket feed was last updated 1 July while its TCGplayer figures were current, so the EUR side would silently go stale.

The DDL is in docs/supabase-schema.sql, including the record_prices(jsonb) function that does the diff inside the database so the job never has to fetch previous values across the network to compare them.
